# 核心设计与边界

本页汇总现行规则，历史问题和实验细节见[归档](archive/README.md)。

## 地点与事实证据

- `poi_id` 表示地图地点，`place_id` 表示地点身份，`item_id` 表示一次行程访问；同名分店不能只靠名称匹配。
- 新增地点必须来自已查询候选。模型的名称、坐标、价格和开放时间不能直接作为地图事实。
- 保留来源、实际取得数据的时间和适用范围。缓存命中不改写取得时间；未知价格、交通和温度不填成 0。
- 生成的游览说明以体验重点为主；操作时间、价格、预约等由结构化字段展示。旧备注不会因过滤规则而被静默重写。
- 官方规则与价格适配只覆盖部分场馆。常规政策参考、地图登记信息、用户确认和实时预约库存是不同证据。

## 排程与修复

时间线包括住宿出发、三餐、景点、返程、真实查询交通、缓冲和等待。缺失交通不补成直线距离估算，也不显示依赖它的精确到达时间。

登记开放时段支持明确钟点、周范围、部分季节格式及停止入场时间。已知闭馆、晚于停止入场或停留跨出窗口均可产生冲突；未知格式、重叠季节、跨夜和不明确例外保留未知。公园与园内场馆的范围分别处理。

新稿可以做有界分区、顺序、本地停留调整和自动餐厅重选。适用的建议停留调整每处最多缩短 25%，并有类型下限；明确时长、必去、锁定及固定预约受相应保护。调整必须重新检查三餐、营业窗口和真实路段，不能靠延长用户窗口或删掉三餐消除冲突。

用户已保存行程的跨日调整需要明确请求。闭馆方案可以移除未受保护的可选景点；保留其余地点和餐厅的相对顺序，避免删掉景点后重新插入午餐造成绕路。仍有冲突或交通不全的候选会明确标示。

## 费用与住宿

门票、每人餐费、每间每晚酒店价格和交通票价按各自口径计算。人数、房间数、预算范围和未知项独立展示；已知参考小计不是完整预订总价。

没有 OTA 实时库存接口时，住宿报价来自用户填写，并绑定入住日期、酒店和房型。普通编辑不应把用户报价改成模型估算；更换条件后不能继承旧的核对状态。一日游不虚增住宿晚数。

## 任务与版本可靠性

- 创建任务使用幂等编号；提交响应丢失后按原编号和原需求恢复，避免重复生成。
- 事务接收、执行租约、续期及令牌检查隔离旧执行者；取消时清理所属的排队查询，共享查询还有其他等待者时继续服务。
- 后台任务、HTTP 耗时操作和供应商 QPS 分层控制。进度读取和取消不应被耗时操作占满。
- 保存检查 `base_version`，变化日期重新校验。预览不写版本，采用和恢复保留版本历史。
- SSE 不可用时退回轮询；临时网络失败可重试，明确的无权限、任务不存在或过期响应停止跟踪，避免永久忙碌。

## 性能与界面

通过精简结构化输出、局部 patch、并行检索、缓存和同请求合并减少重复工作。完全一致的同类 POI 在模型输入中可引用前面的工具结果；变化的事实仍完整展示，服务端保留原始证据。文本字符数不是实际计费 token。

界面以逐日卡片和时间线为主，提供明暗主题、可关闭动效、地图对应、草稿编辑、方案比较和导出。检查失败时提示重试，不能因诊断不可用而显示已经通过。

## 能力声明

“任务完成”“当前参考规则通过”“能实际入场和预订”是不同结论。地图可查到、时间可排下，不代表当天开放、余票可用或场所接待条件已核实。当前证据和未完成工作见[当前状态](STATUS.md)。
