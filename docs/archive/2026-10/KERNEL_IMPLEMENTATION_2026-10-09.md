# 内核优化实施记录

日期：2026-10-09。对应 KERNEL_RESEARCH_2026-10-09.md；本轮为本地实现，未部署。

## 已实现

1. **统一身份**：景点、餐厅和酒店共用 poi_id、place_id、item_id。旧数据生成稳定本地身份，不冒充地图 ID；后续地图查询可补齐。地图证据保留同名分店，显式 ID 不匹配则拒绝。访问 ID 不再依赖排序位置。
2. **局部修改**：PlanPatch 支持添加、替换、移除、排序、停留时长、每日窗口和明确的跨日移动。新增地点由程序从真实候选 ID 装配。修改限定在用户指定日期内，锁定项和预约受保护；已有 DIY 餐厅、酒店、加餐不再被自动补餐覆盖。为旧输出保留完整计划兼容路径，新提示优先使用 patch。
3. **减少重算和上下文**：手动保存仅校验发生变化的日期，未修改日期复用服务端时间表。模型上下文省略交通明细和配图，攻略先发摘要，通过 read_reference 按需读取原文。旧数据的默认字段迁移不产生伪修改版本。
4. **单日求解**：OR-Tools 使用已查询的有向交通耗时，保留所有访问、固定预约和酒店起止锚点。用餐窗口作为软偏好；目标同时考虑交通和全天跨度，避免无谓等待。统一 visit_order 和 planned_start_times，时间线、地图与重新校验沿用同一结果。
5. **交通预算与缓存**：最多检查 24 条候选有向边、最多 18 次访问（酒店出发和返回分别计数）；交通阶段 75 秒预算、单边最多等待 20 秒、求解 2 秒。坐标距离仅用于优先筛选边，未知边不能作为 0 分钟。缓存为进程内缓存 + SQLite 15 分钟缓存，合并同一进程的重复进行中请求。24 是候选边数量，供应商重试和公交失败后的实际步行补查可能增加原始 HTTP 次数。
6. **持久任务**：对话和优化改用后台 PlanningRun，返回任务 ID。页面显示阶段、候选边数量和已用时间，可取消、刷新后重连。Agent 使用 SQLite checkpointer；服务重启恢复未完成任务，已准备结果和最终版本提交有幂等保护。旧版本不能覆盖并发修改。
7. **推荐与质量**：候选不符合偏好时允许模型自行补查至多两次，总模型调用最多三次；按地点 ID 去重与排除。独立质量报告记录日期、必去覆盖、交通覆盖和时间冲突，不把模型完成视为全部事实已核实。公开时间、预约名额仍明确为未核验。
8. **页面衔接**：增加“优化当天路线”，移除编辑页中旧的纯坐标距离排序入口；支持保留安排，显示时间依据和示意地图说明。无天气正文的旧占位数据显示“暂无预报”，不显示占位的 0°C。

## 主要落点

- `backend/app/models/schemas.py`：地点与访问身份、PlanPatch、统一顺序和建议开始时间。
- `backend/app/services/plan_patch.py`：局部操作与只校验变化日期。
- `backend/app/services/schedule_solver.py`：时间窗路线求解及查询预算。
- `backend/app/services/schedule_validator.py`：缓存、真实交通、统一时间线。
- `backend/app/services/planning_runs.py` / `trip_repository.py`：持久任务、恢复、取消和原子提交。
- `backend/app/services/plan_quality.py`：独立覆盖与约束检查。
- `backend/app/agents/travel_agent.py`：局部输出、上下文管理、持久图执行。
- `frontend/src/views/Result.vue` / `services/trips.ts`：优化、进度、重连与取消。

新增接口：POST `/api/trips/{id}/runs`（kind 为 chat 或 optimize，携带 base_version 和 request_id），GET `/api/trips/{id}/runs`、GET `/api/trips/{id}/runs/{run_id}`、POST `/api/trips/{id}/runs/{run_id}/cancel`。request_id 为 UUID，用于安全重试；每次新操作用新 UUID。

## 验证与边界

- 66 项后端离线回归通过，包括分店身份、局部编辑、跨日范围、锁定预约、实际 OR-Tools 求解、未知路线、查询预算、午餐等待、任务取消、幂等提交、并发版本，以及已完成和中断 Agent 检查点恢复。
- 前端 TypeScript 与生产构建通过；仍有原有主包体积提示，未宣称首屏包体问题已解决。
- 真实模型使用公开杭州测试样例，单次模型调用返回 patch 并将停留改为 45 分钟，无地点补查。
- 独立北京验收副本经真实高德查询排程，页面验证进度和刷新恢复，最终路线 4/4 段有实际耗时。原北京三日行程未用于版本修改。
- 当前任务执行、限速与正在执行请求合并适用于**单 worker 本地后端**。多 worker / 多实例需要共享队列、执行租约和共享供应商限流，暂不具备这种部署保证。
- 查询和求解范围有限，成功代表在已核实交通、建议停留与已知约束下可行，不代表全局最优。数据不足或搜索超时不等于证明无解，保留原安排并明确状态。
- 正在执行的外部请求可能在节点恢复时重放；已有结果可复用缓存。checkpointer 不意味着所有供应商调用都“恰好一次”。
- 营业时间、预约可用性、实时价格仍需接入官方来源。自动跨日空间分配、可选地点舍弃与大规模评估数据集仍是下一阶段；本轮跨日修改仅在明确要求下执行，不自动迁移已选日期。
