# 持久任务：原子领取、隔离与故障恢复

本批修复多进程重复执行与旧执行者写入风险，目标是可靠保存结果。它没有完成多实例生产部署验收，外部服务的共享配额、正式账号认证与流量治理仍未完成。

## 实际行为

- SQLite 事务内领取任务，生成独立执行令牌并设置有效期。同一任务在租约有效时不会被其他进程同时领取。
- 进度、prepared结果、失败状态和最终创建/修改旅行都检查当前令牌与有效期。旅行写入和任务成功标记继续处于同一事务；事务期间租约已过期则回滚整次保存。
- 每个数据库默认最多2个任务运行，超过容量的任务保留在持久队列并显示“排队等待处理”。所有使用该库的进程须采用一致配置。
- 默认租约60秒，按不超过1秒的周期续期并观察跨进程取消；失去执行权即停止本执行者。正常关闭时等待正在进行的SQLite操作收尾后释放租约，避免取消线程等待时遗留数据库连接或新租约。
- 后台每2秒扫描未领取/过期任务。强制终止进程后，需要等原租约到期再接管；不是零等待恢复。重试领取默认最多3次，单次处理默认300秒，超时和反复中断会形成可见失败状态。
- prepared结果可直接用于恢复，避免重复执行已经完成的规划；质量状态在保存前重新计算，不继续沿用旧质量结论。
- 每次领取使用独立Agent检查点命名空间，旧执行者不能污染新执行者的图状态。若在prepared结果持久化之前中断，新的尝试可能重新调用模型/地图；不保证外部请求或计费“恰好一次”。
- 租约令牌、有效期及尝试次数不会出现在任务API响应中。旧版本冲突、owner隔离、请求去重和原行程保护继续生效。
- 结果页区分排队与执行；在SSE只有心跳、没有新阶段时，耗时仍持续显示，不会因队列等待看起来停在0秒。

配置已列入 `backend/.env.example`：`PLANNING_MAX_RUNNING`、`PLANNING_LEASE_SECONDS`、`PLANNING_RUN_TIMEOUT_SECONDS`、`PLANNING_MAX_ATTEMPTS`。默认值为2、60、300、3。

## 健康检查的范围

`/health` 仍为进程存活检查。`/ready` 另检查本地恢复执行器是否运行、迁移后的SQLite是否能被访问；未就绪返回503。它不调用模型/高德，明确返回 `upstreams=not_probed`，不能据此证明外部配额或凭据实时可用。

本次仅更新现有单进程本地服务。即使任务存储已具备跨进程领取与提交隔离，也不建议仅据本批测试开启生产多worker：高德当前限速器仍是进程内状态，共享配额治理尚待实现。SQLite也未验证跨主机/网络文件系统部署。

后续已经补上同部署内的SQLite共享请求许可，见 [共享限流验证](SHARED_LIMITS_2026-10-16.md)。真实多worker负载、不同主机和账号级配额仍未验收；本地服务继续保持单进程。

## 验证证据

- 完整后端回归227项通过，15.066秒；日志 `backend/var/job-leases-regression.log`。新增覆盖并发领取、旧令牌、保存事务中到期、心跳、远程取消、反复取消、线程中领取时取消、容量、超时、恢复次数、prepared恢复和质量重算、旧库迁移及就绪检查。
- 独立子进程故障验证4项通过，报告 `backend/eval/results/job-reliability-20261016-145053.json`。通过 `venv/Scripts/python.exe -X utf8 -m eval.job_reliability` 可重跑，全部使用临时库与合成生成器，不调用模型/地图服务。

| 故障场景 | 生成器调用/保存 | 结果 |
| --- | --- | --- |
| 两进程竞争同一任务 | 1次 / 1份 | 成功，无重复生成 |
| prepared后强制终止进程再恢复 | 1次 / 1份 | 复用prepared结果成功保存 |
| 原执行者仍活着但租约过期，被新进程接管 | 2次 / 1份 | 两个检查点命名空间，旧令牌写入被拒绝 |
| 从另一进程取消 | 1次 / 0份 | cancelled，不保存 |

这些是任务调度与数据一致性的证据，不是实际模型速度、规划准确率或多用户负载测试。
