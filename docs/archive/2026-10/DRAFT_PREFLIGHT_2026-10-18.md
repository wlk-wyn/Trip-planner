# 初稿预筛、当前行程问答与报价保留（2026-10-18）

本阶段改善规划前的无效顺序、已保存行程问答的准确性，以及手动编辑后的报价可信度。整体生产可用性仍未证明，尤其没有酒店实时报价或库存接口。

## 初稿预筛

`draft_density.py` 只处理完整、尚未生成时间线的自动初稿；明确要求、固定预约、锁定地点、严格攻略及明确时长等不进入这项自动调整。先在同一天内有界尝试顺序，保留所有地点、停留时长、餐饮和酒店。本地搜索最多 64 次、0.15 秒，不访问模型或地图。

仍然过密时最多进行一次模型建议复核，整个预筛等待预算为 5 秒。提案必须保持地点集合和每日数量，可选建议时长最多缩短 25%，并受现有最低停留限制；不必要的缩短会有界恢复。登记营业时间和出行缓冲仅能形成乐观下界，预留交通预算不是查询结果。所有候选仍须后续真实路线与完整性检查，不能伪造时间线或消除未知事实。

公开杭州初稿冻结回放 `backend/eval/results/density-replay-20261018-061254.json`：22.1 毫秒，无模型和网络调用，仅调整第二天顺序，地点、时长和餐饮全部保留，没有生成虚假时间线。这个结果只证明该初稿可提前避免无效顺序，不证明最终交通可行。

## 读取当前行程

`current_itinerary.py` 对“当前每天安排了哪些景点”这类高置信只读问题直接读取当前结构化地点与通过完整性检查的时间线，不搜索新地点或调用模型。推荐、修改、费用、开放情况、可行性等问题继续交给 agent。缺失或无效时刻明确待校验，每日出发窗口不能解释为入园时间。

公开同一快照问答的旧失败记录 `overview-question-20261018-061406.json` 保留：模型用 4.071 秒、两次模型调用并搜索了两次地点，虽答对景点却把 09:00 出发误说成入园。修复后的 `overview-question-fast-20261018-061913.json` 用 0.682 秒（含 agent 构造），模型调用为零，返回已保存的故宫 12:57—15:57、天坛 11:15—13:26，原行程未改动。这不是通用生产延迟指标。

新生成行程的每日及整体说明从最终地点生成，避免修复后的路线仍带有已移除地点的旧正文。备选调整记录单独标明；已有用户行程和手写说明不批量重写。

## 住宿参考报价

没有 OTA 权限时继续使用按日期、酒店身份绑定的用户房型报价与条件性住宿预留，不把模型金额当作实时报价。税费不明时保留预算不完整状态。

本轮修复一般手动编辑可直接改写或带入 `nightly_quote` 的问题：普通编辑只复制服务端同一日期、同一酒店访问且身份和费用字段一致的原报价；不能借整份行程保存创建、改写或移动报价。更换酒店、访问身份、地址、坐标或费用后清除旧报价。报价更新继续使用专门的入住日期报价接口，原有版本撤销功能保留。

完整后端回归：**541 项通过，29.788 秒**，日志 `backend/var/current-readiness-tests.log`。新增报价测试覆盖普通编辑注入、改写、跨日期移动、更换酒店、无关说明修改保留，以及隔离数据库的真实 API 保存后读回。未对用户原数据库提交测试行程或报价。
