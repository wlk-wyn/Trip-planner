# 完整规划评测与由真实失败推动的修复

## 评测覆盖

`backend/eval/run_eval.py run` 现在走页面使用的持久创建任务：生成、地点/交通/时段检查、门票参考估算、保存到临时 SQLite，再读取实际保存结果评分。测试行程不写入用户数据库。

- 区分任务完成、参考检查通过、可直接执行三个结论；营业与预约没有官方证据时 execution_ready 仍为 false。
- 校验城市、首尾日期与逐日日期；检查时间线与真实地点、顺序、停留时长和交通端点是否一致，防止空时间线、错路段或旧时长冒充通过。可识别旧版访问 ID，不改写旧记录。
- 认为可行的时间线必须有合法时刻、完整停留、必要交通与缓冲，且分项和总时长一致。出现此类异常时前端提供重新校验入口。
- 预算不足的数据返回 unverified，而非用未知价格 0 宣告通过；已列参考费用超过预算时判为未通过。当前尚不能用已列费用证明全程总预算满足要求，人数、完整交通与准确住宿晚数等仍需完善。
- 用例约束仅覆盖明确声明的可计算条件，不把所有自由文本偏好视为已自动验证。未实现的评测条件、拼错的 case ID、空 case 集不静默跳过。
- 支持重复执行和超时取消，按 case 分别汇总时延、失败、超时；成功样本不足 20 不输出生产 p95，达到 20 也不代表统计置信或并发压测已完成。
- 新报告保存公开合成请求、输出快照、逐日冲突/缺失路段原因、阶段耗时及模型用量，可完全离线重新评分。中途保留增量报告。
- `--check` 可作回归门禁，任一参考检查未通过则返回非零退出码。

复现示例（backend 目录）：

```powershell
venv/Scripts/python.exe -X utf8 -m eval.run_eval score
venv/Scripts/python.exe -X utf8 -m eval.run_eval run --cases cs-walk-1d,hz-slow-elder-2d,xa-budget-3d --timeout 180 --check
venv/Scripts/python.exe -X utf8 -m eval.run_eval replay --report eval/results/run-20261016-105948-017835.json --check
```

score 只读检查已存快照，不能将历史示例或人工验收行程混入真实生成准确率。run 使用现有缓存，没有把冷/热缓存分别归类；不可从单次耗时推算稳定提速。

请求日期为运行日往后 21 天，均是公开构造用例，无用户原行程外发。第一轮完整结果在 `backend/eval/results/run-20261016-105207-602501.json`。

## 根据证据修复

1. **进度倒退**：缓存批量完成时，异步 SQLite 写入可能把后面的 5/7 覆盖回 2/7。每个任务的进度写入现已串行化，并有刻意延迟早期写入的回归测试。页面可以跳过过快阶段，但同一阶段不会因写入乱序回退。
2. **餐厅遗留在被移除区域**：杭州重跑快照指出，诗野·小院回酒店公交无方案，步行又超过安全替代上限；初稿删掉远处景点后自动餐厅仍原地保留。
   - 新行程修复现在重新检查系统自动匹配且偏离新路线的餐厅。
   - 手选、锁定、结构化必去匹配或请求中完整点名的餐厅保留；初稿之外的已保存行程不自动重排。
   - 找不到新候选时保留原餐，不通过删餐隐藏失败。新餐厅仍来自地图查询并重新验证真实路线。
   - Meal.route_matched 是本批服务端生成时设置的来源提示，不是账号权限或可信认证。
3. **评测暗中访问模型**：两个创建任务单元测试现在明确替换非本测试目标的门票估算，避免单元测试误调用真实模型。门票估算逻辑另有专项测试，真实完整评测仍执行它。

修复后杭州两天的最新完整快照：`backend/eval/results/run-20261016-105948-017835.json`。这次为 38.38s，11/11 路段取得耗时，两天均无时间冲突，当前参考检查通过。仍有 4 项未知价格，execution_ready=false。模型选择的酒店与行程也变化，不能将两次时延差归因于单一修复。

最新快照已离线 replay 并通过参考门禁：`backend/eval/results/replay-20261016-110124-484281.json`。西安的营业时段冲突仍是后续需要处理的真实失败，没有因杭州通过而清除它。
