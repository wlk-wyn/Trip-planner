# 查询合并与冷缓存稳定性（2026-10-18）

本轮针对真实规划 `load-20261018-050821.json` 中出现的路线磁盘缓存失效，以及相同地点冷查询重复发往供应商的问题。提高已有额度下的资源利用率，没有调整高德额度或用缓存替代缺失证据。

## 复现及改动

离线复现 `backend/eval/results/cache-fanout-before-20261018.json` 使用临时 SQLite 文件，五轮各 32 个不同缓存键并发读写。每轮均触发一次缓存警告与 30 秒退避，写入后命中为零。同一合成地点的 32 个并发请求发出 32 次底层查询。这些是本地合成测试，没有真实地图调用。

`schedule_validator.py` 现在先在事件循环中排队，再执行缓存 I/O，避免多个执行器线程同时初始化 WAL/表。同步适配器也有进程内锁；只对 SQLite BUSY/LOCKED 做最多四次短重试，其余故障继续降级。SQLite 的 WAL 在连接关闭清理及恢复等情况下仍可能返回 BUSY，参考 [SQLite 官方说明](https://www.sqlite.org/wal.html#sometimes_queries_return_sqlite_busy_in_wal_mode)。

缓存读取最多等队列 0.2 秒，背景写入最多等 1 秒；实际 I/O 另有 0.2 秒观察上限。排队拥挤只跳过本次缓存，不把健康存储判成故障后退避 30 秒。背景写入不阻塞已经得到的路线结果。线程中的 SQLite 操作不能被异步超时强制停止，因此执行前固定目标路径，保留同步锁和连接关闭，避免迟到操作换到其他存储。

`amap_rest.py` 对同一事件循环内完全相同的地点详情、文本搜索、周边搜索及照片请求共享一个在途任务。查询类型、城市、关键词、数量、类别、城市限制、坐标和半径仍参与各自缓存键。每个调用者得到独立深拷贝，保留实际观测时间；错误不缓存，空结果保留原有缓存规则。

取消一个等待者不取消其他人的查询；最后一个等待者离开会取消底层任务，在配额等待阶段取消时不会发 HTTP。关闭服务会等待查询清理后关闭传输连接。合并仅限单进程同一事件循环，不声称跨进程只查一次；供应商共享配额协调保持原有逻辑。新增指标仅为计数，不记录地点、密钥或请求内容。地图计数功能不再提前导入模型运行库。

## 实测

| 验证 | 结果与收据 |
| --- | --- |
| 最终离线冷缓存 | `cache-fanout-after-20261018-052611.json`：五轮各 32/32 命中，零警告、零整体退避；同一地点 32 请求共用 1 次合成查询 |
| 独立进程共享缓存 | `disk-workers-20261018-052437.json`：四进程同步启动，三轮各 32/32 正确记录、零错误、`integrity_check=ok`；运行时 SQLite 3.53.2 |
| 真实高德地点查询 | `poi-fanout-20261018-052331.json`：32 个 ASGI API 请求全部 200，1 次高德 HTTP、31 次共享加入、后续缓存命中，来源时间相同；共 0.192 秒 |
| 本地主服务真实 HTTP | `cache-live-http-20261018.json`：正常入口控制下 6 个并发公开午门请求全部 200、来源时间相同，共 0.132 秒；不据此推断供应商请求数 |
| 路线缓存与取消 | `route-reliability-20261018-052609.json`：六种合成场景全部通过；清空内存后的磁盘命中无需新供应商调用，保留原查询时间，失败/无效耗时仍不冒充有效路线 |

收据均在 `backend/eval/results/`。ASGI 测试是进程内接口派发，未配置完整 HTTP 入口控制；真实 HTTP 另按当前每来源并发限制使用六请求验证。二者不是同一个负载实验。时间只是这些请求的观测值，不是生产 p95。失败前缓存测试没有完成有效写入，不能把其较短墙钟时间用于计算提速倍数。

调试中的中间结果保留：最初一次整体排队超时触发过退避；另一次把背景写入也限制为 0.2 秒排队，出现 28/32 命中。随后将队列拥挤与存储故障分开，并给不阻塞路线返回的背景写入独立等待预算。没有覆盖这些中间收据。
