# 取消规划后的查询清理（2026-10-18）

本轮针对取消后的服务容量与响应性，不宣称完整规划已经提速或达到生产可用标准。上一阶段公开两日任务仍需约 40–46 秒，当前未重新进行付费模型或真实高德负载测试。

## 复现与修复

旧 `validate_schedule` 通过 `asyncio.wait` 等待多段交通，但调用者被取消时没有取消子任务。八景点、七段交通的受控测试中，外层已报告取消，仍有四个请求处于执行中，另三个排队请求也没有被清理。失败日志保留在 `backend/var/schedule-cancel-before.log`；不能只依赖 planning run 的 `cancelled` 状态判断查询已停止。

现在校验器在成功、超时、异常和取消路径都收集自己的子任务；未完成任务会取消并等待清理。重复取消不会打断这项清理。最后一个共享路线消费者退出时，也等待该共享查询结束；仍有其他消费者时保留查询。超时仍返回明确的未知交通与超时提示，不把缺失耗时写为零。

进一步的实际路由集成测试发现，FastAPI 同步取消接口运行在线程池，旧代码在这个线程直接调用事件循环任务的 `cancel()`。新代码把取消投递到任务所属循环；SSE 订阅记录各自的循环，跨线程通知也投递到该循环。已有数据库所有权、版本与租约约束继续生效；跨进程执行仍通过共享状态和租约心跳感知取消，本轮没有将它改为跨进程即时中断。

## 验证范围

新增 `backend/tests/test_schedule_cancellation.py` 七项覆盖：

- 取消时结束四个执行中请求，三个排队请求不进入供应商，随后新校验可以完成。
- 连续取消仍等待供应商清理。
- 两个校验共享路线时，取消一个不影响另一个。
- 校验截止后保留未知耗时及提示。
- 通过实际 FastAPI 路由创建、取消、查询任务，等待执行器结束；隔离数据库没有保存半份旅行或版本。
- 工作线程通知能唤醒 SSE 使用的事件循环订阅，并可正常退订。
- 实际地图请求适配器、串行限流锁、独立 SQLite 配额协调器配合模拟 HTTP：第一个 HTTP 已发送后取消，等待超过一个配额间隔，发送数仍为 1；随后新校验成功，累计变为 2。没有向真实供应商发送数据或使用其额度。

集成测试使用 ASGI 内进程 HTTP，模拟外部查询，不是浏览器操作或生产压力测试。第一次集成验收在旧跨线程取消路径挂起，终止的仅为对应测试进程；修复后重新运行。限流测试的 10 QPS 只用于合成配置，生产高德限额没有提高。

完整后端回归 **548 项通过，30.018 秒**，见 `backend/var/cancellation-final-tests.log`。用户原数据库仍为六份行程、十五份版本和三个已成功任务；本阶段未提交测试数据到原行程。

## 剩余工作

这项修复避免已取消任务继续排队抢占额度，不能降低正常完成一份行程所需的真实交通查询数。正常规划的请求量、路线修复成本、真实并发延迟、外部服务权限、酒店库存、官方开放与预约信息覆盖仍需继续验收，整体生产目标保持未完成。
