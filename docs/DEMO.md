# 求职演示与讲解

目标：用五分钟展示一个能规划、能修改、能解释不确定信息的旅行助手。当前交付是本地演示版和可部署配置，容器及公开体验入口仍待目标环境验收。

## 开始前

按[运行说明](RUNNING.md)启动前后端。在仓库根目录执行 `./scripts/check-demo.ps1`，检查页面入口、后端和本地存储就绪；这个命令不会调用模型、地图或新增行程。

已有依赖和配置时可直接运行 `./scripts/start-demo.ps1`，复用或启动本项目服务并检查就绪。离线走通 API 闭环可在 `backend` 目录执行 `./venv/Scripts/python.exe -X utf8 -m eval.demo_journey --report var/demo-journey.json`：该脚本使用临时数据库和受控交通，不会改动私人行程或调用供应商，也不能替代真实生成和现场页面展示。

首页的三个主题可补全空白城市与日期。日期使用未来的周二，仍可手动更改；已填城市、日期和攻略保留。选择主题只填写需求，点击“开始规划”才会调用服务。刷新会保留当前标签页尚未发送的文字和表单。

演示新建一条旅行，不用已有的私人行程练习。录屏时隐藏环境配置、请求头和个人数据。

## 五分钟演示顺序

| 时间 | 操作 | 要表达的能力 |
| --- | --- | --- |
| 0:00—0:40 | 选择城市漫游，确认日期，点击开始规划 | 自然语言和结构化条件共同输入，不必先填长表单 |
| 0:40—1:30 | 查看生成进度；生成后切换日期、定位地图 | 持久任务、逐日阅读、真实路段耗时；等待时可解释流程 |
| 1:30—2:30 | 打开编辑，搜索并替换一个景点或餐厅，预览后保存 | 用户可 DIY；改动后需要重新核对路线和时间，不只是改文字 |
| 2:30—3:20 | 打开查票窗口，读官方须知；用明确标注的示例录入预订费用并预览 | 实付总额替代对应人数的参考费；跳转不等于已订票，示例不保存到私人行程 |
| 3:20—4:15 | 录入示例入场时段，展示晚到提示、提前出发或换序方案；查看预算变化 | 时段参与排程，变化路段重新核实，可行方案先预览再保存 |
| 4:15—5:00 | 查看并恢复历史版本，刷新；说明退款与未知费用的边界 | 可追溯和可恢复，取消记录不等于退款到账；预算仍有明确口径 |

遇到供应商超时，展示错误和重试/恢复入口；不要重复点击新建多个任务。失联与取消的受控验证见前端 `pendingPlan.test.mjs`、`runWatcher.test.mjs`，并发写入与恢复见后端 `test_saved_trips.py`。这些自动化检查不能代替现场浏览器操作。

可选替换费用展示环节：打开景点“查门票与预约”，在窗口内阅读官方须知，再展开“行程入场时间”。用演示行程录入一个早于预计到达的最晚入场时间，展示冲突与提前出发方案；选择后先预览，再决定保存或关闭。演示值只是排程约束，不能称为已购买门票或真实余票。保存后可通过版本恢复撤销；不要在私人行程中保存示例时段。

“寻找其他调整方案”会查变化路段，有界搜索可能返回未知或无解；展示这一结果及原因，不能用其他示例替换后称为该次查询成功。价格读取可在后台进行，官方须知、入场检查和费用录入独立工作。继续问答、餐厅推荐、明暗模式可作为扩展展示，不必全部挤进五分钟。

## 面试讲解

开场可以这样介绍：

> 我做的是一个支持自然语言需求和攻略输入的旅行助手。模型负责选择和解释地点，程序使用地图路段、停留时间和营业约束检查安排。用户可以修改景点、餐厅和酒店，保存版本并继续询问助手。

三个值得展开的工程问题：

1. **生成内容如何落地**：模型输出绑定已查询地点身份；真实交通和可解析营业时间参与排程。缺失证据保留为未知，不能把未知耗时当成零。
2. **修改如何可靠**：编辑不是重新生成整段答案；局部修改经过校验和版本检查，过期版本返回冲突，恢复有历史记录。
3. **延迟和成本如何控制**：地点与路线缓存、查询合并、共享 QPS、有界修复、模型上下文投影。用实际调用次数和样本耗时回答，不宣称全部请求都能在固定秒数内完成。

数字与已验证范围统一引用[评测](EVALUATION.md)。当前没有正式账号体系、全面实时预订、公开并发与长期稳定性结论，不把这些写成已实现功能。
